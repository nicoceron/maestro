# API conventions

The versioned contract is [`packages/contracts/openapi.yaml`](../../packages/contracts/openapi.yaml). Update the contract and generated declarations in the same change as an API behavior change.

## Authentication

First-party browser clients authenticate through Laravel Sanctum's stateful session cookie. Mutating requests also send the URL-decoded `XSRF-TOKEN` cookie value in the `X-XSRF-TOKEN` header. Browser requests must include credentials. The Laravel application must keep Sanctum stateful middleware, trusted domains, credentialed CORS, session cookie attributes, and the contract aligned in every environment.

The browser begins with `GET /sanctum/csrf-cookie`. Headless Fortify routes live under `/api/v1/auth`: login, logout, forgot/reset password, verification consume/resend, password confirmation/status, TOTP, passkeys, and current-user lookup. Maestro's public-registration controller owns `POST /api/v1/auth/register` so registration cannot inherit Fortify's auto-login response. Registration and login normalize email with Unicode whitespace trim, NFKC, and lowercase. Forgot-password returns the same `202` message for known and unknown syntactically valid emails and uses HMAC-derived account limiter keys. Password reset applies the uncompromised-password rule, rotates the remember token, removes the user's database sessions, and revokes the user's Sanctum personal access tokens.

Registration may optionally carry an invitation token. A semantically valid pending token bound to a genuinely new normalized email permits creation of only the unverified global user. Registration never verifies the user, accepts the invitation, creates a membership, or changes the server-owned invitation role. Explicit sign-in plus onboarding or `POST /api/v1/invitations/accept` performs that later transition.

Every syntactically valid registration request returns `202` with `{ "message": "If registration can be completed, check your email for next steps." }`, including a new email, an existing normalized email, or an unusable, terminal, or email-mismatched invitation. The response never claims creation or delivery, never redirects, and never authenticates or rotates the browser's existing CSRF session. Only a genuinely new eligible user is persisted and receives the encrypted, queued, after-commit verification notification; all other accepted cases are no-ops. Input-shape, email-syntax, password-confirmation, minimum-12-character, and compromised-password failures remain ordinary `422` validation errors and are evaluated before any account lookup result can affect the public response. Passphrases are permitted; character-composition rules are not part of the accepted contract.

Accepted registration work performs the password hash on every semantic path and uses a 300 ms minimum timebox so new, existing, and unusable-invitation cases share a bounded timing class. HMAC-derived limiter keys permit five requests/hour per normalized-email-plus-IP and 20/hour per IP; the shared 60/minute auth-form IP ceiling also applies. A limited request returns `429`, and no limiter key contains a raw email. The Next.js client ignores server-provided account-specific success copy, displays fixed generic guidance, and performs no current-user probe or onboarding redirect after `202`; ordinary public registration never probes identity. An invitation landing may make one pre-render current-user probe solely to route an already-authenticated recipient to onboarding, while keeping the fragment scrubbed and retaining it only for a later authenticated flow.

Reset and invitation email credentials are carried in URL fragments so they are not sent in HTTP request targets. The Next.js landing code reads each fragment once, immediately scrubs it from browser history, and submits the credential only in a CSRF-protected JSON body. Laravel enforces trusted hosts/request origins and emits production security headers. Fortify identity, TOTP, passkey, and invitation-preview responses are non-cacheable.

TOTP setup is a two-step transition: enable creates encrypted pending setup material for at most ten minutes, and confirmation with a valid six-digit code activates it. A confirmed account receives `two_factor: true` after password login and must complete the five-minute, rate-limited challenge using a current TOTP or one-time recovery code. The server rejects replay of the same TOTP time step. Reading setup secrets or post-confirmation recovery codes, recovery-code regeneration, and disablement require a recently confirmed password or passkey; recovery-code routes are unavailable until TOTP is confirmed.

Fortify's WebAuthn routes provide usernameless passkey login, same-session passkey confirmation, and recently confirmed registration/deletion. Relying-party ID and allowed origins are exact configuration boundaries, user verification is required, challenges are session-bound/single-use, and a dedicated limiter protects ceremonies. `GET /api/v1/auth/passkeys` exposes only safe metadata; credential IDs and public-key material are never serialized.

Password/passkey confirmation remains valid for at most ten minutes in production. `GET /api/v1/auth/sessions` lists opaque public session ULIDs, server-derived device labels, coarse network prefixes, created/last-seen timestamps, and a current marker; raw IP addresses, user agents, and backend session IDs are withheld. Expired and orphaned registry rows are pruned during inventory. The two DELETE routes revoke one owned session or all other browser sessions and require recent confirmation; revoking the current session logs that browser out. Standard sessions have a maximum eight-hour idle and 30-day absolute server-side lifetime, configurable downward. Session expiry returns `401` even when a browser still holds its cookie.

Privileged-role MFA enforcement/grace policy, platform-specific shorter sessions, security notifications, cross-domain immutable audit, delegated support, and a reusable idempotent outbox remain explicit acceptance gaps; endpoint presence alone does not complete them. Identity controls are fixed in [`../security/identity-access-acceptance.md`](../security/identity-access-acceptance.md); the platform audit/support/outbox and tenant lifecycle target is fixed in [`../product/platform-operations-acceptance.md`](../product/platform-operations-acceptance.md).

The current global `User` resource uses Laravel's existing positive bigint ID. Studio, membership, invitation, household, person, and other tenant-domain resources use ULIDs. Clients must not assume one identifier format for every resource.

## JSON envelopes

- A single resource is `{ "data": { ... } }`.
- Creation responses add a fixed `message` alongside `data`.
- The current studio list is deliberately unpaginated and returns `{ "data": [{ ... }] }`.
- The studio invitation list is paginated at 25 records and returns top-level `data`, `links`, `meta`, and server-derived `capabilities`.
- The People list is paginated from 1 through 100 records (default 25) and returns top-level `data`, `links`, `meta`, and `capabilities.can_create`.
- The household list is paginated and returns top-level `data`, `links`, and `meta`. Laravel 13's `meta.links` entries include `url`, `label`, `page`, and `active`.
- Scheduling-configuration, overdue-attendance, attendance, note, note-template, tenant-export, and deletion-request lists use Laravel length-aware `data`, `links`, and `meta` envelopes. Calendar, audit, and support-grant lists are cursor-based and have no total/page count.
- Future endpoints must document the envelope their controller actually returns; pagination is not implied globally.

## Errors

Laravel API failures use a JSON problem envelope with a required human-readable `message`. Validation failures use status `422` and add an `errors` object whose keys are input paths and whose values are arrays of messages. Scheduling, attendance/note, support-access, and tenant-lifecycle conflicts add a stable top-level machine `code`; `423` distinguishes missing recent confirmation or MFA from authorization. Clients should branch on HTTP status, `code`, and field keys, not localized message text.

## Studio routing

Studio IDs are ULIDs, but the `{studio}` route parameter is the unique studio slug because `Studio::getRouteKeyName()` returns `slug`. Listing includes only the authenticated user's active memberships and is sorted by studio name. Cross-tenant access returns `403`; an unknown slug returns `404`.

## Onboarding

`POST /api/v1/onboarding` accepts exactly one of `invitation_token` or a `studio` creation intent. Invitation onboarding accepts the invitation's server-locked role and matching email. New-studio onboarding requires a verified email and creates an owner membership only when the user has no active membership; a user who already has one receives their earliest active studio instead of another automatic studio. The response is the ordinary `Studio` resource plus `Onboarding completed.`

`preferred_name`, `workspace_mode`, and `primary_goal` merge into membership preferences. `workspace_mode` (`owner`, `administrator`, or `teacher`) is never an authorization input: it cannot choose the new membership role or override an invitation. The request rejects both top-level `role` and `studio.role`.

## Invitations

`POST /api/v1/invitations/preview` is public and rate-limited and accepts `{ "invitation_token": "…" }`. A valid pending token returns only `status`, a masked `email_hint`, and `expires_at`; it intentionally omits the studio, role, inviter, account state, and full email. Invalid, expired, revoked, and accepted tokens return the same unavailable response. The retired bearer-path routes are not registered.

Owners and administrators can list invitations for an active route studio. The list accepts `q` (maximum 100 characters), `status`, `role`, and one-based `page`; it returns server-authorized `capabilities.can_create` and `capabilities.invitable_roles`. Owners can invite administrator, office, billing, and teacher roles. Administrators can invite office, billing, and teacher roles. Owner invitations are invalid because ownership requires a separate transfer workflow. Creation normalizes the email and returns `201` with `message: "Invitation queued."` and a safe invitation resource; authorized tenant-local pending/member conflicts may return `422` without disclosing global-account or other-studio state.

The public invitation resource is intentionally allowlisted to `id`, normalized `email`, `role`, `status`, lifecycle/delivery timestamps, `send_count`, `resend_available_at`, `delivery_status`, server-derived `permissions`, and `created_at`. It never exposes bearer/digest material, account state, queue/outbox identifiers, or internal lineage/version identifiers.

Create, resend, and revoke require password or passkey confirmation no older than ten minutes. After route binding, active-studio membership authorization, recent-credential confirmation, and mutation role-policy authorization succeed, creation is limited to 20 attempts/hour per inviter and 100 attempts/day per route studio; rejected non-members, role-denied members, or unconfirmed callers do not consume those sensitive quotas, and quota rejection returns `429` before invitation, delivery, audit, or job effects. `POST /api/v1/studios/{studio}/invitations/{invitation}/resend` takes no body and returns `202` with the fresh replacement resource and `message: "Invitation resend queued."` A pending or expired predecessor can be renewed after cooldown; the old row is superseded and its bearer is unusable before the response. The route enforces one attempt/minute and three replacements/day per lineage only after the same authorization and recent-credential checks. Accepted, revoked, superseded, or otherwise ineligible tenant-local rows use the `422 invitation` family, the route throttle and persistent quota use `429`, and cross-tenant substitution is `404`. Revocation is pending-only; an already revoked row is idempotent `204`, while accepted, expired, and superseded rows return `422 invitation` with `This invitation cannot be revoked.`

Authenticated `POST /api/v1/invitations/accept` accepts the same JSON token body and requires the token email to match the current normalized global email. It atomically creates the active membership with the invitation's server-side role, marks the invitation accepted, and verifies the matching email. Repeating acceptance by the same active member returns the same joined `Studio` resource; mismatches and unusable states share an `invitation_token` validation error.

PostgreSQL forced RLS protects both studio memberships and invitations. Authenticated requests establish the current user database context, tenant routes additionally establish the route studio, and token preview/registration establish only the digest-scoped invitation context needed for that transaction.

Invitation creation and resend commit a unique pending delivery intent. After commit, the encrypted unique mail job's invitation-domain payload contains only the invitation ULID and internal delivery version, alongside Laravel's framework queue metadata; the worker re-resolves tenant and terminal state at execution and suppresses stale work. The one-minute recovery scheduler redispatches pending intents. Immutable, forced-RLS tenant events cover create, queue, delivery/suppression, resend/supersession, revoke, accept, and digest redaction. A daily non-overlapping command redacts terminal invitation digests after 30 days without deleting rows or duplicating audit events. Exact privacy rules and stable evidence IDs are fixed in [Invitation audit and delivery acceptance](../security/invitation-audit-delivery-acceptance.md). This is an implemented invitation-domain foundation, not evidence that all platform security writes use an immutable audit/outbox. Same-user accepted-token replay deliberately derives an idempotent `200` from the terminal membership state; it does not require a client idempotency key or create a second membership/event.

## People and student lifecycle

`GET /api/v1/studios/{studio}/people` supports case-insensitive `q`, person `status`, `student_status`, `staff_role`, tenant instrument/tag ULIDs, exact normalized `source`, `per_page` from 1 through 100, and one-based `page`. Results are ordered deterministically by last name, first name, then ULID. Owners, administrators, office staff, and billing staff can read; teachers cannot. Billing search matches names and payer-visible contact data only; billing callers may use `q`, `status`, and pagination, while syntactically valid student, staff, taxonomy, and source filters return `403` because those dimensions are private (ordinary parameter validation can return `422` first). The collection returns the server-derived `capabilities.can_create` decision.

Owners, administrators, and office staff can atomically create and PATCH people with optional student/staff profiles, tenant tags and instruments, and definition-typed custom-field values. Cross-studio identifiers and newly assigned inactive taxonomy fail with `422` and roll back the complete mutation; an already assigned inactive tag or instrument may be preserved during edit. Submitted assignment arrays replace their collection; omitted fields remain unchanged. An existing student or staff profile is history-bearing and cannot be deleted: students use the lifecycle transition action and staff move to `former`. Student `left_on` is response-only and derived by the lifecycle transition; create/PATCH payloads cannot write it directly.

Person responses always retain the same field shape. Billing sees contact data only for a person who receives billing and otherwise receives `null`; birth date, pronouns, source, external reference, locale, staff details, taxonomy, custom fields, and transition history are withheld as `null` or empty arrays. Non-payer billing views also receive `student: null`. No response includes `studio_id`, linked global `user_id`, status-history `actor_id`, join-row identifiers, normalized taxonomy keys, or soft-delete metadata.

`PATCH /api/v1/studios/{studio}/people/{person}` and `POST /api/v1/studios/{studio}/people/{person}/student-status` require the current person `version`. Stale state returns `422 version` without partial mutation. Creating a student profile appends an immutable initial event whose `previous_status` is `null`; later status transitions are limited by the server-owned lifecycle graph, update relevant lifecycle dates, increment the parent version, and append one immutable tenant-scoped history record. Person IDs resolve only through the route studio; cross-studio and non-student substitution returns `404`. Browser mutations require both the Sanctum session and Laravel XSRF cookie/header pair.

This is a scaffolded CRM foundation, not a completed People module. Full guardian/adult-student lifecycle, interactive merge, bulk actions beyond data portability, ownership/link verification, complete role matrix, audit/outbox adoption, and production-size accessibility/E2E coverage remain required. The implementation follows [Laravel 13 API resources](https://laravel.com/docs/13.x/eloquent-resources), [pagination](https://laravel.com/docs/13.x/pagination), [validation](https://laravel.com/docs/13.x/validation), [authorization](https://laravel.com/docs/13.x/authorization), and [Filament 5 resource security](https://filamentphp.com/docs/5.x/advanced/security).

## CRM data portability

CRM portability lives under `/api/v1/studios/{studio}/data-portability`. Active owners, administrators, and office staff can download the simple CSV template and operate their own artifacts; billing, teachers, learner/guardian roles, and delegated support cannot. Import/export artifacts are requester-only, so another otherwise authorized studio manager receives nondisclosing `404`. Staging, resolution, commit/resume, export creation, diagnostic download, signed-URL issuance, and signed download require identity confirmation and current-session MFA no older than ten minutes. Status, cursor-paginated row-plan reads, and preview use the ordinary active portability-role session; every browser mutation remains CSRF-protected.

`POST .../imports` accepts a multipart `file` plus an 8–128 character `Idempotency-Key`. The current implementation recognizes either a bounded UTF-8 People CSV or a decrypted `.maestro` CRM portable JSON bundle. `POST .../imports/{import}/preview` takes the current `import_version` and an optional source-heading-to-canonical-field mapping. Preview performs no People mutation. For a daily CSV, valid no-match rows auto-plan `create`; exact/probable/ambiguous and same-file duplicates stay `conflict`. `GET .../imports/{import}/rows` returns safe source-order pages with an opaque row-plan ULID, `plan_version`, safe preview fields, tenant-local candidate IDs/versions, and outcome fields. It omits the raw row, storage paths, hashes, global identities, queue identifiers, and exception detail. `PUT .../resolutions` accepts at most 200 create/update/skip CSV decisions under both the import and row-plan versions; it deliberately uses no additional resolution bearer token.

A `.maestro` bundle v1 is an empty-target restore, not a merge. Preview and commit reject a nonempty CRM target with `409` code `CRM_PORTABLE_TARGET_NOT_EMPTY`; every bundled person is planned `create`; atomic bundle commit is capped at 5,000 people with `409` code `CRM_PORTABLE_ROW_LIMIT_EXCEEDED`; and the resolution endpoint rejects bundle decisions with `409` code `CRM_PORTABLE_DECISIONS_FORBIDDEN`. A sequential commit-time drift test is live. Restricted-PostgreSQL proof that a concurrent ordinary CRM write cannot race the empty-target check remains acceptance work.

Commit and resume create durable idempotent commands and queue bounded worker chunks. Status is read through the import resource; sanitized diagnostics are available at `GET .../errors.csv`. The intended problem boundary is `401` for no session, role-policy `403`, requester/tenant/expired/purged `404`, typed idempotency/version/state `409`, CSRF `419`, shape/content `422`, step-up `423`, and bounded quota/rate `429`. Until the CRM-specific problem mapper and complete matrix tests land, callers must treat this exact error family as acceptance work rather than assume every branch is already stable.

`POST .../exports` queues one private encrypted-at-rest export. A ready requester-only projection omits its storage path, ciphertext/archive hash, request fingerprint, actor, failure digest, and job metadata. `POST .../exports/{export}/download-url` issues a five-minute signed application route; the signed GET reauthorizes and atomically permits one decrypted `application/vnd.maestro.crm-portability+json` `.maestro` download. The bundle contains a checksummed manifest and deterministic formula-safe UTF-8 CSV datasets for People, student/staff profiles, households/guardian links, instruments/tags, and custom fields.

This surface is `scaffolded` in the parity ledger. The live scaffold has an exact 12-dataset schema/dependency allowlist, portable source-to-target reference remapping, a small empty-target round trip, focused restricted-PostgreSQL RLS/round-trip checks, production configuration guards, and an accessible browser journey. Full acceptance still requires a real database snapshot boundary; shared two-process concurrency proof for the empty-target restore; lifecycle/action authorization and rollback proof for every restored dataset; crash/resume and production-size evidence; exhaustive restricted-PostgreSQL concurrency/RLS cases; deterministic Unicode, multiline, formula, null/empty fuzz/golden bundles; safe purge fault injection, object-delete retry, and orphan reconciliation; and complete configuration matrices. The normative matrix is [CRM data portability acceptance](../product/crm-data-portability-acceptance.md).

## Households

`GET /api/v1/studios/{studio}/households` accepts an optional case-insensitive `q` search across household and member names, `per_page` from 1 through 100 (default 25), and a one-based `page`. Pagination URLs preserve the supplied query string. The collection is sorted by household name.

Households are aggregate roots containing members, people, optional learner profiles, guardian relationships, portal permissions, timestamps, an aggregate version, and caller-specific `edit` and `delete` permissions. Household IDs and all nested entity IDs are ULIDs. A household ID is always resolved through its studio relationship, so a cross-studio ID returns `404`.

The creation payload uses request-local member keys to connect guardians and learners before ULIDs exist. It must contain exactly one primary contact with an email address or phone number. Learners require a student profile, non-learners cannot have one, relationship keys must point to the appropriate member roles, and a guardian/learner pair can appear only once.

`PATCH /api/v1/studios/{studio}/households/{household}` requires the current household `version`. Omitting `members` preserves the member and guardian graph. Supplying `members` atomically replaces household membership; each response member exposes `person.version`, retained people send that value with their tenant-scoped `person_id`, and new people omit both. Relationships may be replaced only with members and default to an empty replacement when omitted. Stale aggregate/member state, cross-studio person IDs, and attempts to remove or transition an existing student profile return field-keyed `422` without partial mutation. Removed household members remain studio people.

Active owners, administrators, office staff, and billing staff can view households. Owners, administrators, and office staff can create or edit; only owners can delete. Teachers cannot access household records. An unrelated or suspended studio membership returns `403` before tenant-scoped household work runs.

## Scheduling configuration

The registry-backed `/api/v1/studios/{studio}/scheduling/{resource}` API covers service categories, services, effective prices and policies, locations, rooms, equipment and room stock, program offerings and teacher/location overrides, teacher-account links, scheduling limits, recurring availability, availability/time-off overrides, and directional travel buffers. Every reference is validated inside the route studio, and composite PostgreSQL constraints provide a second boundary for room/location/equipment and tenant identity. Responses omit `studio_id` and normalized keys, expose policy-derived edit/retire capabilities, redact private location/equipment details outside management, and hide approval/enforcement state from a teacher's time-off projection.

Configuration updates are PATCH-only and require the current `version`; stale state is a field-keyed `422` and commits nothing. History-bearing configuration is retired with `active=false`; there is no delete route. Effective price, policy, and offering-override periods cannot overlap. Program-offering GET can resolve effective values for a date, teacher, and location and returns each field's source. Teacher self-service is limited to an explicitly linked active staff profile. Local override inputs use an IANA zone and wall-clock `Y-m-dTH:i:s`; DST gaps and unresolved folds are rejected. Management decides time off through the dedicated versioned approval route, and approved time off is always a hard constraint.

## Calendar, recurrence, and schedule commits

The public calendar exposes only scheduled, non-hold occurrences from active public series. It never returns tenant IDs, enrollment or assignment identities, prices, internal descriptions, or online join credentials. The authenticated calendar applies one role projection: scheduling managers receive operational details, linked teachers receive only assigned work and may filter only their own linked staff profiles, and billing receives a restricted projection without location or teaching details. Both range queries are bounded to 93 days. Cursor pagination prevents a large studio from receiving a silently truncated calendar.

Event-series creation, clone, roster changes, reschedule, cancellation, and restoration use preview then commit. A preview canonicalizes bounded RFC 5545 recurrence, resolves local times explicitly across DST, detects non-overrideable hard conflicts and manager-acknowledgeable soft warnings, snapshots every referenced aggregate version, and expires after ten minutes. It exposes only impact, typed conflicts, projection intents, expiry, and capabilities—not the stored command, hashes, actor, tenant, or internal versions. Billing, payroll, and conditional make-up entries are projection intents at this boundary; this milestone does not create financial ledger effects.

Commit endpoints accept no replacement command or warning acknowledgement and require an `Idempotency-Key` of at most 100 characters. The server reauthorizes, locks, validates actor/studio/command binding and TTL, compares the aggregate snapshot, fingerprints warnings, reruns conflicts, and then applies the server-stored command. Reusing the same actor/tenant key for the same normalized command returns the original projection; using it for another command returns `409 idempotency_key_reused`. Cross-actor/cross-studio preview lookup returns `404`. Holds expire within seven days and are converted or released with current version plus idempotency; release retains canceled history. Slot search is advisory, scans at most 31 days, excludes hard conflicts, ranks candidates by soft warnings, and does not reserve a result.

The recurrence and scheduling core is still scaffolded rather than parity-complete. External calendar sync, production-scale query/load proof, comprehensive concurrent booking/ranking scenarios, and full UI regression coverage remain acceptance work. See [Scheduling and attendance acceptance](../product/scheduling-attendance-acceptance.md).

## Attendance

Attendance supports `present`, `late`, `absent_excused`, `absent_unexcused`, `no_show`, and `teacher_cancelled`. The API derives billing and make-up dispositions from the immutable occurrence policy snapshot; clients are prohibited from supplying either. Assigned teachers and scheduling managers can record one learner, atomically record up to 250 distinct participants, or mark every still-unrecorded eligible participant present. An edit requires the current version and, when normalized state changes, a nonblank correction reason. The original row identity remains stable and an immutable correction record captures the previous version. Every write is actor-scoped and idempotent.

Management can list attendance work overdue after a caller-selected past cutoff (24 hours by default). Management receives correction history. Billing can read outcome and billing disposition but receives null learner identity, lateness, reason, and make-up details and cannot mutate attendance. An authorized learner/guardian sees only linked participant records, including canonical teacher-cancelled history after the participant is canceled. Attendance-driven invoice, payroll, make-up-credit ledger, and offline synchronization remain separate planned capabilities.

## Lesson notes, delivery, and attachments

Lesson notes are participant- or group-scoped and addressed to the student, guardian, or author only. HTML is sanitized through a strict allowlist; scripts, event handlers, remote images, and tracking markup do not survive. Every edit requires the current optimistic version and appends an immutable revision. Billing cannot access notes. Management has compliance visibility; an assigned teacher sees other distributable notes and only their own `author_private` notes; learner/guardian reads require the corresponding portal relationship and active occurrence roster.

Templates use the same audience enum and sanitizer. Management creates, versions, and retires them; teachers see only active templates. Delivery is also preview/commit: the preview binds the note version, eligible recipient fingerprint, and current clean attachment metadata. Commit rejects expired/consumed previews and note, recipient, or attachment drift with a typed `409`, records one immutable delivery intent plus transactional outbox message, and returns the original projection on exact idempotent replay. Provider delivery remains asynchronous.

Attachments are never public objects. Upload is multipart with `note_version`, an actor-scoped idempotency key, extension/MIME/file-magic agreement, configurable count/byte budgets, and a default 25 MiB per-file maximum. PDF, PNG, JPEG, WebP, MP3, M4A, WAV, and OGG are accepted into private quarantine and passed to a fail-closed malware scanner. Pending, failed, infected, and retired files are not downloadable. Editors can see retained current-revision metadata, including unsafe and retired states, to retry or audit it; learner/guardian projections include only current clean active metadata. The API never reveals storage disks/keys, quarantine paths, scanner internals, or a permanent URL.

A clean attachment download begins with a short-lived signed application URL. The download route rechecks its signature, active studio membership, current note authorization, clean/unretired state, and a recent password or passkey at use time. Retirement immediately revokes an already issued URL, retains immutable history, and never physically deletes the domain record. Byte responses are private/no-store, `nosniff`, and CSP-sandboxed.

## Immutable audit and delegated support

`GET /api/v1/studios/{studio}/audit-events` is an owner/administrator cursor projection of the forced-RLS append-only audit stream. Filters cover event type, safe subject type, correlation ULID, occurrence range, and a bounded page size. The response allowlist is `id`, `event_type`, safe subject and actor labels, `correlation_id`, `payload_version`, event-type-allowlisted `payload`, and `occurred_at`. It never exposes global actor IDs, request/network/client hashes, support bearer material, stream hashes/sequences, outbox state, or another studio.

Platform support is separate from studio membership. After recent password/passkey confirmation, `POST /api/v1/platform/support-access/mfa-confirmation` verifies a six-digit TOTP and gives only the current browser session ten minutes of support-access MFA assurance; an invalid code is `422 support_mfa_invalid`, and a missing/expired proof on a support mutation is `423 support_current_session_mfa_required`. The endpoint returns only `verified` and `expires_at`, never authenticator material. An active platform operator then submits `POST /api/v1/platform/support-access/requests` with one studio ULID, a 12–500 character purpose, a window of at most four hours, an `Idempotency-Key`, and only `audit.read`, `configuration.read`, `people.read`, `schedule.read`, or `diagnostics.read`. These are read-only declarations; there is no export, credential, legal-hold, deletion, restore, ownership, billing-secret, or arbitrary-write scope. Studio owners/administrators approve, reject, or revoke a route-studio request with an optimistic `version`; a dual-role platform operator can never approve their own request. Recent password/passkey confirmation and current-session MFA are required for every support mutation and session start.

An approved operator starts a maximum two-hour session. The start response discloses the high-entropy bearer once; only an HMAC digest is stored. Every support-session call combines the operator's Sanctum session with `X-Maestro-Support-Session`, rechecks the active platform assignment, exact operator/session/grant/studio, window, revocation, and required scope, and emits no-store plus visible support-context headers. The banner names the studio, purpose, scopes, approver, and expiry. The operator identity remains the actor; Maestro never creates or serializes a tenant-user impersonation session. PostgreSQL grants the support session a select-only capability policy; it never sets the ordinary tenant context and cannot use delegated audit access to read adjacent tenant tables or write the audit stream. The currently exposed delegated read is the redacted tenant audit stream. Configuration/People/schedule/diagnostics support readers and complete per-view audit evidence remain acceptance gaps, so FND-07 is scaffolded rather than done.

The reusable outbox foundation assigns one monotonic aggregate sequence, encrypts a bounded versioned payload, records correlation and idempotency keys inside the caller transaction, dispatches only after commit, leases due messages with a claim token and expiry, rejects stale acknowledgements, retries with bounded backoff, dead-letters on exhaustion, and iterates tenants under explicit database context. Audit and support workflows use it. Cross-domain migration, consumer inbox deduplication, jitter/SLO telemetry, alert evidence, and production concurrency/load proof remain FND-09 gaps.

## Tenant export, retention, deletion, and restore drill

Tenant-data routes are owner-only and require recent password/passkey confirmation plus current-session MFA for every mutation, signed download, and restore drill. Export and deletion creation use an `Idempotency-Key` header. Exact input replay returns the original resource; changed reuse is typed `409`. Export generation is asynchronous and private. A ready export has a short-lived one-use signed application download; authorization, MFA, membership, signature, state, and expiry are rechecked at use time. The response is a no-store `application/vnd.maestro.tenant-export+json` envelope, not a raw database dump.

The manifest declares format/schema, export and snapshot timestamps, application schema, tenant timezone/locale/currency, canonicalization, excluded secret fields, media-inventory choice, and each ordered NDJSON dataset's path, dependencies, version, count, byte length, and SHA-256. The API returns only the safe manifest projection and never storage paths/ciphertext hashes, request fingerprints, queue state, failure digests, or actor IDs. Password/session/reset/invitation/MFA/passkey/PAT/provider/encryption/storage and queue secrets are excluded. Attachment media inventory is metadata only; the export does not contain attachment bytes.

The retention surface exposes versioned TTL/cooling/quarantine/operational/media/audit settings and a studio-wide legal hold. Policy update is optimistic. Legal hold placement/release is recently authenticated, MFA-protected, locked, and audited; an active hold blocks deletion progression and export expiry. This is not yet the target scoped legal-hold aggregate with separate approval and subject/class/time boundaries.

Deletion request requires the exact `DELETE {studio-slug}` phrase, a specific reason, a ready unexpired final export whose encrypted object and complete archive checks verify again at approval, independent approval by a distinct active studio administrator, no legal hold, and the configured 14-day cooling-off period. Deletion-bound export retention covers the cooling-off and quarantine windows. Maestro permits one active owner, so the requesting owner cannot approve their own request. Scheduled progression suspends ordinary tenant routes and enters 30-day quarantine; only the narrow authenticated lifecycle read/cancel/restore control plane remains available. Cancellation is locked and idempotent. This tranche deliberately does not hard-delete tenant rows/files/keys. Restore reverses the retained pre-suspension studio and membership statuses. Separately, a restore drill is a non-writing asynchronous verification of the current Maestro archive envelope, schema, checksums, declared entries, byte/row counts, JSON rows, source-tenant invariants, and one tenant-ID remap. It does not upload/import/merge/activate an archive or prove rollback after activation. Exact full-release requirements remain in [Platform operations acceptance](../product/platform-operations-acceptance.md), so FND-10 is scaffolded rather than done.
